# 05 · 代码 / diff → 单元与回归测试

## 输入

```text
【被测代码】
{{文件路径 / diff / 整个模块}}

【现有测试】
{{测试目录、框架、fixture/mock 约定、历史用例}}

【覆盖率】
{{coverage.json / jacoco.xml / lcov.info / 未覆盖行}}

【约束】
- 语言/框架: {{Python/pytest | TS/Jest | Java/JUnit}}
- 是否允许网络/DB: {{否 / 是}}
- 是否允许修改生产代码: {{否}}
- 超时: {{...}}

【输出】
实际测试文件 + 可选 case 摘要
```

## 任务

### 阶段 1：分析

- 公开行为/契约：输入、输出、异常、副作用。
- 分支与边界。
- 依赖：DB、HTTP、时间、随机、文件、消息。
- 现有测试风格与 fixture 约定。

### 阶段 2：生成测试

必须：

- 可编译、可运行、无网络（除非明确允许）；
- 使用现有 fixture/mock 风格；外部依赖用 mock/fake；
- 断言行为/契约，不直接断言私有实现细节；
- 每条测试只验证一个行为；
- 覆盖未覆盖分支/边界/异常；
- 包含正常、边界、异常、幂等/并发（适用时）；
- 测试数据固定、可重复、可清理；
- 不修改生产代码；不引入新依赖（除非说明理由）。

### 阶段 3：执行与反馈

1. 运行测试，必须全部通过。
2. 看覆盖率增量；没有增量的测试删除或改写。
3. 跑变异测试（如可用）：
   - 存活变异体 → 补测试；
   - 等价变异体 → 说明理由并跳过。
4. 连续运行 3 次，检查 flaky。

### 阶段 4：输出

- 完整测试文件（或 unified diff）。
- `cases` 摘要：测试名、目标文件/行、技术、理由。
- 运行命令。
- 无法测试的部分及原因。

## TDD 模式（可选）

如果用户要求 TDD：

1. 先写失败测试（red）；
2. 确认失败原因正确；
3. 再写最小实现（green）；
4. 重构；
5. 用 TDD Guard / Probity 强制“先测试后实现”。

## 质量红线

- 禁止 `assert True` / 只调用不检查。
- 禁止复制实现逻辑到测试里。
- 禁止依赖执行顺序/共享状态。
- 禁止测试私有方法（除非是必要的契约）。
- 禁止为了覆盖率生成无意义参数化。
