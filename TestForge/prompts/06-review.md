# 06 · 用例评审 / 去重 / 覆盖审计

## 输入

```text
【需求/AC】
{{requirements 或 testable-items.json}}

【用例集】
{{test-cases.json / e2e-cases.json}}

【团队规范】
testforge/templates/case-template.md

【输出】
.testforge/reports/review.md
.testforge/reports/review.json
```

## 任务

不要直接重写全部内容；先诊断，再给最小修改。

### 评审维度（每条 0-2 分）

1. **需求追溯**：每条 AC 是否被覆盖？是否有孤儿用例？
2. **技术覆盖**：EP/BVA/DT/ST/权限/异常/幂等/并发是否缺失？
3. **可执行性**：步骤是否具体？数据是否明确？预期是否可判定？
4. **预期依据**：是否有文档/代码依据？是否臆造？
5. **原子性**：一条用例是否只验证一个主要目标？
6. **去重**：是否存在语义重复？给出合并建议。
7. **独立性**：是否依赖执行顺序/共享状态？
8. **可自动化**：是否适合自动化？需要什么 fixture？
9. **优先级**：P0/P1 是否合理？
10. **风险覆盖**：高风险路径是否有足够用例？

### 输出

- `score`：总分与各维度分数；
- `blocking_issues`：必须修复的问题（用例 ID、证据、建议）；
- `coverage_gaps`：未覆盖的 AC/技术/风险；
- `duplicates`：重复组与合并建议；
- `rewritten_cases`：仅给出需要重写的用例；
- `gap_list`：需要产品/开发确认的信息；
- `verdict`：`PASS`（≥16/20 且关键三项 ≥1）/ `REVISE` / `REJECT`。

### 评分规则

| 维度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 需求追溯 | 无来源 | 部分有 AC/章节 | 每条可追溯到 AC + 源章节 |
| 技术覆盖 | 只有 happy path | 有正/负例 | EP/BVA/DT/ST/权限/异常按需覆盖 |
| 步骤可执行 | 空泛 | 有步骤缺数据 | 字段/值/操作/预期均可执行 |
| 预期依据 | 明显臆造 | 部分有依据 | 全部有依据，未定义入 Gap |
| 原子性 | 多目标混合 | 少量混合 | 一条一个主要目标 |
| 去重 | 大量重复 | 少量重复 | 语义去重且有合并说明 |
| 独立性 | 依赖顺序 | 部分依赖 | 可独立执行、可重复 |
| 可自动化 | 不可自动化且无说明 | 部分可自动化 | 标注 automatable 并给 fixture 需求 |
| 优先级 | 未标注/不合理 | 基本合理 | 与风险和业务价值匹配 |
| 风险覆盖 | 未识别高风险 | 部分覆盖 | 跨服务/异步/并发/权限等高危路径覆盖 |

## 输出纪律

- 每条问题必须带用例 ID 和证据（原文/来源）。
- 不要用“建议优化”这种空话；给出可执行的修改。
- 不要为了让分数好看而放过高风险缺口。
- 如果材料不足，直接 `REJECT` 并列出需要补充的材料。
